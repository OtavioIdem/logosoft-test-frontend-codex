## 1. Objetivo

`npm run validate:contract-fields` e `npm run validate:contract-request-fields` passam a fazer parte de `ci:gates`
e do job `frontend-gates` do workflow, e `validate:ci` passa a cobrar os dois nominalmente — do mesmo jeito que já
cobra os outros `validate:*`.

## 2. O achado, medido

- **Ausência em `ci:gates`**: `node -e` sobre `package.json.scripts['ci:gates']` antes desta fatia devolvia
  `false` para `.includes('npm run validate:contract-fields')` e para
  `.includes('npm run validate:contract-request-fields')`.
- **Ausência no workflow**: `.github/workflows/frontend-ci.yml` (antes desta fatia, 115 linhas) não tinha nenhum
  step com esses dois `run:`.
- **Os dois gates passam hoje**: `npm run validate:contract-fields` → exit 0, "Nenhuma divergência detectada.".
  `npm run validate:contract-request-fields` → exit 0, "Nenhuma divergência crítica detectada." com 8 LACUNA
  (`AtualizarDadosFiscaisProdutoRequest.tipoItemSped/unidadeTributavelSigla/exTipi/codigoBeneficioFiscalPadrao`,
  `VincularProdutoFornecedorRequest.descricaoFornecedor`, `TransferirEstoqueRequest.origemId/documento`,
  `AtualizarEmpresaRequest.contribuinteIpi`). Ligar não quebra o CI.
- **Por que ninguém notou**: `test:unit` (`vitest run tests/unit tests/components`) está em `ci:gates` e roda a
  prova durável dos dois gates (`tests/unit/gateContractFields.test.ts`,
  `tests/unit/gateContractRequestFields.test.ts`), mas nunca executa os scripts `gate-contract-*.mjs` como parte
  do pipeline de produção — só como sonda dentro do teste, contra árvores montadas em espelho. O script em si
  nunca era invocado pelo CI.
- **A prova durável estava vermelha desde a b63, sem que ninguém tratasse**: medido com `git worktree add` sobre
  `4e589f7` (commit da b63) e `node scripts/gate-contract-request-fields.mjs` executado diretamente naquela
  árvore: a saída lista **10** "Campos anuláveis sem destino na UI", e `AdmitirColaboradorRequest.pessoaId` não
  aparece nem entre os críticos nem entre as 10 lacunas — está ausente da saída inteira. O arquivo de teste
  daquele mesmo commit (`tests/unit/gateContractRequestFields.test.ts` em `4e589f7`, linhas 90-94 e 329-345)
  esperava **11** LACUNA e, entre elas, nominalmente `AdmitirColaboradorRequest.pessoaId`
  (`it('imprime LACUNA: AdmitirColaboradorRequest.pessoaId')`) — ou seja, a asserção `expect(saida).toContain('11')`
  e a que busca a string `AdmitirColaboradorRequest.pessoaId` teriam falhado se `test:unit` tivesse corrido contra
  aquele estado. A `b64` já registrou este achado no seu próprio `CHANGELOG.md` ("Achado à parte, medido nesta
  sessão") e reparou a prova (Bloco C da b64, LACUNA_ESPERADOS_HOJE passa a ter 8 itens). Hoje, na árvore corrente,
  `npx vitest run tests/unit/gateContractFields.test.ts tests/unit/gateContractRequestFields.test.ts` dá **77
  passed** — a prova está verde de novo, mas **por causa da b64**, não por qualquer correção de processo desta
  fatia. **A b63 continua tendo sido commitada com `test:unit` vermelho**: isso é falha de processo e não é
  corrigido aqui.

## 3. Decisões desta fatia

Sem `Dn` nova: a mudança é mecânica (ligar dois comandos já existentes e já verdes) e não abre discussão de
desenho. A classificação de `risk` (MEDIUM, não CRITICAL) é arbitrada pela sessão principal: o precedente
`v1.11.0a8b57.c1` era CRITICAL porque o gate cego tinha divergência real na árvore corrente (16 pares de menu
fora do que o gate via); aqui os dois gates já passam limpos, então ligar não reprova ninguém hoje — o risco que
resta é o de um PR futuro que hoje passaria sem ser cobrado pelos dois gates.
