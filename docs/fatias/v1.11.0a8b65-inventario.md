Contrato do `ProdutoResponse`, `docs/BACKEND-ESTADO-ATUAL-E-CONTRATO.md:3141`, conferido contra

## 3. Round-trip de cada campo — o achado que muda a fatia

`ProdutoResponse` devolve **todos os cinco campos do recorte** (mapeados 1:1,
`ProdutoMapper.cs:44,46-47,49-51`): `TipoItemSped`, `UnidadeTributavelSigla`, `ExTipi`,
`CodigoBeneficioFiscalPadrao` aparecem na resposta; `DescricaoFornecedor` aparece em
`ProdutoFornecedorResponse.cs:140` (`Guid Id, Guid FornecedorId, string CodigoFornecedor, string?
DescricaoFornecedor, bool Principal, EntityStatus Status`) dentro do array `Fornecedores` do mesmo
`ProdutoResponse`. Isso responde a primeira metade da pergunta — sim, o backend devolve os cinco.

A segunda metade — **mantém ou apaga quando vem `null`** — tem duas respostas diferentes, porque
são dois use cases com semântica distinta:

### `AtualizarDadosFiscaisProdutoRequest` — **não é "mantém" nem "apaga campo a campo". É substituição atômica do bloco inteiro, com uma trava que hoje bloqueia a gravação.**

`AtualizarDadosFiscaisProdutoUseCase.ExecutarAsync` (`:71`) chama
`_dadosFiscais.ResolverAsync(request, unidadeComercial?.Sigla, ...)` **sem** passar os dados
fiscais atuais do produto — não há merge. `ProdutoDadosFiscaisResolver.ResolverAsync` tem dois
caminhos (`:45-56`):

```csharp
if (EstaEmBranco(request))
{
    // Bloco fiscal em branco = limpar a parametrização. [...] nada é apagado além dos
    // próprios campos de parametrização.
    return Result.Success(DadosFiscaisProduto.Vazio());
}

if (!request.TipoItemSped.HasValue)
{
    return Result.Failure<DadosFiscaisProduto>(CadastrosFiscaisErrors.TipoItemSpedObrigatorio);
}
```

`EstaEmBranco` (`:173-183`) só é `true` se **os dez campos** do request estiverem nulos/vazios ao
mesmo tempo. Fora isso — ou seja, sempre que **qualquer** campo do bloco fiscal é enviado — o
resolver exige `TipoItemSped` como obrigatório, e devolve `400 FISCAL_CADASTROS_TIPO_ITEM_SPED_OBRIGATORIO
— "Tipo do item no SPED (Registro 0200) é obrigatório quando o bloco fiscal é parametrizado."`
(`CadastrosFiscaisErrors.cs:154-157`). `Produto.DefinirDadosFiscais` (`Produto.cs:173-193`)
sobrescreve os 15 campos fiscais do agregado de uma vez, sem `?? valorAtual` em nenhum deles — não
existe a semântica "campo não veio, mantém o que já tinha" que a D54/CRT tinha. Aqui a semântica é:
**bloco inteiramente vazio → limpa tudo; bloco parcialmente preenchido sem `tipoItemSped` → falha**.

**Isso não é uma lacuna teórica — é um defeito ativo na árvore de hoje.** O schema atual
(`produtosSchemas.ts:97-104`, 6 campos) nunca envia `tipoItemSped`. E o `ProdutosPage.tsx:81-94`
(`save`) chama `dadosFiscaisMutation` **sempre** que o usuário tem `PRODUTOS_DADOS_FISCAIS_GERENCIAR`
— inclusive na criação de produto novo, onde `ProdutoFormDialog.tsx:85` fixa
`tipoItemFiscal: TipoItemFiscal.Mercadoria` como valor inicial do formulário (não é `null`). Como
`tipoItemFiscal` tem valor por padrão, `EstaEmBranco` já dá `false` na criação do primeiro produto —
e cai direto no `if (!request.TipoItemSped.HasValue)`, que falha. **Hoje, para qualquer usuário com
`PRODUTOS_DADOS_FISCAIS_GERENCIAR`, criar um produto novo dispara uma chamada PATCH
`/api/produtos/{id}/dados-fiscais` que o backend rejeita com 400**, e o toast de erro do
`ProdutosPage.tsx:99` ("Erro ao salvar produto") aparece depois que o produto e (na edição) o
preço/custo já foram gravados com sucesso — o `runWithToast` de `save()` não usa `rethrow: true`,
então o estado fica parcialmente salvo sem indicação clara de qual sub-chamada falhou.
Não encontrei teste unitário ou E2E que exercite esse round-trip HTTP real:
`tests/unit/produtosPayload.test.ts:63` só verifica a forma do payload Zod, não a resposta do
backend; os dois E2E que citam `validarDadosFiscaisProduto` (`tests/e2e/fiscal-backend.spec.ts:114`,
`tests/e2e/integrated-backend.spec.ts:186`) são flags de cenário, não montei evidência de que
exercitem o clique real de "Salvar produto" com o backend de pé — **não verificado**.

Preencher os quatro campos que faltam em `AtualizarDadosFiscaisProdutoRequest` nesta fatia não é só
"acrescentar campo": é o que **destrava** a gravação do bloco fiscal, que hoje falha sempre que
qualquer campo dele é informado. Isso muda o enquadramento da fatia de "campo fiscal novo" (como
está registrado em `LACUNA_DESTINO` do gate, `scripts/gate-contract-request-fields.mjs:363-366`)
para "corrigir perda de gravação", equivalente em gravidade ao D54 do CRT, mas com uma diferença:
o D54 apagava em silêncio; aqui o backend **recusa** com 400 em vez de gravar dado errado — o
sintoma visível para quem testar é "não consigo salvar dados fiscais de produto", não um campo
silenciosamente vazio.

### `VincularProdutoFornecedorRequest` — sem risco de apagar; é criação, não atualização

`VincularFornecedorProdutoUseCase.ExecutarAsync` (arquivo completo lido) chama
`_repository.ExisteFornecedorVinculadoAsync(produto.Id, request.FornecedorId, ...)` e recusa se já
existe vínculo (`ProdutoErrors.FornecedorJaVinculado`) — **não há update de vínculo existente**, só
criação (`Produto.VincularFornecedor`, `Produto.cs:226-241`, sempre `ProdutoFornecedor.Criar(...)`).
Não encontrei nenhum use case `AtualizarFornecedorProduto` no diretório
`../New project 3/src/Erp.Application/Produtos/` (grep por `VincularFornecedor` só achou o create).
Logo `descricaoFornecedor` ausente hoje não apaga nada — simplesmente grava `null` na criação do
vínculo, que é o comportamento correto para um campo opcional numa operação de `INSERT`.

`PRODUTOS_DADOS_FISCAIS_GERENCIAR` **não** está nesse `anyOf`, mas isso é esperado: a rota de

**Catálogo de unidades tributáveis exige `FISCAL_CADASTROS_CONSULTAR`?** Sim —
`CadastrosFiscaisController.cs:152`. Esse código já existe no union e no catálogo

## Divergências

1. **Achado central — round-trip:** `AtualizarDadosFiscaisProdutoRequest` recusa (HTTP 400,
   `FISCAL_CADASTROS_TIPO_ITEM_SPED_OBRIGATORIO`) qualquer chamada onde o bloco fiscal não está
   inteiramente vazio e `tipoItemSped` não foi enviado (`ProdutoDadosFiscaisResolver.cs:45-56`).
   O schema atual (`produtosSchemas.ts:97-104`) nunca envia `tipoItemSped`, e
   `ProdutoFormDialog.tsx:85` fixa `tipoItemFiscal: TipoItemFiscal.Mercadoria` como padrão de
   criação — o que faz `EstaEmBranco` retornar `false` mesmo num produto novo sem nenhum dado
   fiscal digitado. Efeito medido por leitura de código (não por execução): toda criação de
   produto por usuário com `PRODUTOS_DADOS_FISCAIS_GERENCIAR` dispara uma chamada PATCH que o
   backend rejeita. Não encontrei teste que exercite esse caminho HTTP real — **não verificado
   em runtime**, só por leitura de código dos dois lados; marcado como achado porque as duas
   pontas (schema que nunca manda `tipoItemSped` + validação que passa a exigi-lo assim que
   qualquer outro campo do bloco é enviado + valor default não-nulo no form de criação) fecham o
   caminho sem exceção.
2. **Campo entregue pelo backend que a UI ignora (tipo incompleto):** `ProdutoResponse` do C#
   devolve `NcmId`, `CestId`, `OrigemMercadoriaId`, `TipoItemSped`, `UnidadeTributavelOficialId`,
   `UnidadeTributavelSigla`, `GeneroItem`, `ExTipi`, `CodigoBeneficioFiscalPadrao` — nove campos
   fiscais que `features/produtos/types/produtos.types.ts:56-83` (`ProdutoResponse` do frontend)
   não declara. O tipo frontend só tem `ncm`, `cest`, `origemMercadoriaCodigo`, `tipoItemFiscal`,
   `unidadeMedidaTributavelId`, `codigoFiscalExterno`. Cinco desses nove (`TipoItemSped`,
   `UnidadeTributavelSigla`, `ExTipi`, `CodigoBeneficioFiscalPadrao`, e o par
   `NcmId`/`CestId`/`OrigemMercadoriaId` como Ids) fazem parte ou são vizinhos diretos do recorte
   desta fatia.
3. **Enum fixo no frontend sem enum correspondente no backend (ao contrário — aqui é o inverso):**
   `TipoItemSped` existe no backend (`TipoItemSped.cs`) e **não existe** em `types/erp.ts` — union
   sem enum, não enum sem union. Registrado porque o padrão do módulo (`TipoItemFiscal`,
   `TipoProduto`, ambos espelhados em `types/erp.ts`) sugere que `TipoItemSped` deveria ter o
   mesmo tratamento, e hoje não tem.
4. **Campo lido pela UI (response) que o request equivalente não cobre:** `VincularFornecedorProdutoRequest`
   do frontend (`produtos.types.ts:178-182`) não tem `descricaoFornecedor`, mas
   `ProdutoFornecedorResponse` do mesmo arquivo (`:48-54`) já tipa `descricaoFornecedor?: string |
   null` — a tela consegue **exibir** um valor que nunca teve como **enviar**. Consistente com o
   item já registrado em `docs/fatias/v1.11.0a8b58.c3-contratos-de-request.md:320`.
5. **Rótulo ambíguo, não é bug de contrato mas é risco de confusão de implementação:** o campo já
   existente no formulário rotulado "Unidade tributável" (`ProdutoFormDialog.tsx:266`) aponta para
   `unidadeMedidaTributavelId` (catálogo interno, Mód.03) — correto pelo contrato. Esta fatia
   introduz `unidadeTributavelSigla` (catálogo oficial global, Mód.04), que também se chama
   "unidade tributável" em qualquer nome natural de campo. Ver §2.
6. **Permissão de catálogo não coberta pela guarda da tela:** a aba fiscal do produto é guardada só
   por `PRODUTOS_DADOS_FISCAIS_GERENCIAR`; resolver `unidadeTributavelSigla` contra o catálogo
   oficial exige adicionalmente `FISCAL_CADASTROS_CONSULTAR` (`CadastrosFiscaisController.cs:152`).
   Não há hoje nenhum código no módulo Produtos que verifique essa segunda permissão — porque o
   catálogo ainda não é consumido. Precedente idêntico já resolvido em Administração/Endereço
   Fiscal na `b64` (`useEnderecoFiscalCatalogos.ts:10`, `EnderecoFiscalFormSection.tsx:212,295`).
7. **Gate `LACUNA_DESTINO` (mapa auxiliar no script, não no teste):** `scripts/gate-contract-request-fields.mjs:356-369`
   mapeia cada um dos 5 campos do recorte para `'b65'`; se os schemas forem atualizados sem tocar
   este mapa, o gate continua passando (o teste conta 3, não 8, corretamente), mas o relatório
   humano do gate passa a imprimir `?` como destino para qualquer LACUNA nova que reaproveite os
   mesmos nomes — não é falha de teste, é perda de legibilidade do relatório. Registrado como
   risco, não como bloqueio.
8. **Endpoint fora da allowlist:** não se aplica — `scripts/backend-contract-map.allowlist.json`
   não lista os dois endpoints do recorte (`dados-fiscais`, `fornecedores`) nem o catálogo de
   unidades tributáveis em `legacyReferences`, e nenhum dos três está em desacordo com o contrato
   (`CriarProdutoRequest`/rotas batem 1:1 com o C#) — logo não é achado, é ausência esperada.
