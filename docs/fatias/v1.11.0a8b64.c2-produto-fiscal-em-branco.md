## 1. O defeito

`PATCH /api/produtos/{id}/dados-fiscais` **falha hoje** nos dois caminhos da tela de Produtos.

O backend resolve o bloco fiscal em `ProdutoDadosFiscaisResolver.ResolverAsync`
(`../New project 3/src/Erp.Application/Produtos/ProdutoDadosFiscaisResolver.cs:44-56`):

```csharp
if (EstaEmBranco(request))
{
    // Bloco fiscal em branco = limpar a parametrização. Não é erro …
    return Result.Success(DadosFiscaisProduto.Vazio());
}

if (!request.TipoItemSped.HasValue)
{
    return Result.Failure<DadosFiscaisProduto>(CadastrosFiscaisErrors.TipoItemSpedObrigatorio);
}
```

E `EstaEmBranco` (`:173-183`) exige que os **dez** campos estejam nulos — incluindo
`!request.TipoItemFiscal.HasValue`.

Ou seja: **basta um campo fiscal preenchido para `tipoItemSped` virar obrigatório.** O schema
`atualizarDadosFiscaisProdutoSchema` (`features/produtos/schemas/produtosSchemas.ts:97-104`) tem
seis campos e `tipoItemSped` não é um deles — não existe caminho no frontend que o envie.

### Como isso chega no operador

| Caminho | O que a tela manda | O que o backend faz |
| --- | --- | --- |
| **Criar produto** | `ProdutoFormDialog.tsx:85` fixa `tipoItemFiscal: TipoItemFiscal.Mercadoria` nos valores padrão; `ProdutosPage.tsx:92-93` dispara o PATCH logo após criar | `EstaEmBranco` = false → `TipoItemSpedObrigatorio` → **400** |
| **Editar produto já classificado** | `ProdutoFormDialog.tsx:55-64` carrega `ncmCodigo: record.ncm`, `tipoItemFiscal: record.tipoItemFiscal`, `origemMercadoriaCodigo`, `unidadeMedidaTributavelId` do registro | idem → **400** |

Nos dois casos o `saveMutation` (e, na edição, o `precoCustoMutation`) **já gravou** quando o PATCH
falha. O `runWithToast` mostra *"Erro ao salvar produto / Não foi possível salvar o produto"* — uma
mensagem que nega o que de fato aconteceu: o produto está lá, só o bloco fiscal não foi.

### Duas classes de defeito, nomeadas

1. **`DEFAULT_SILENCIOSO`** — `tipoItemFiscal: TipoItemFiscal.Mercadoria` na criação é um valor que
   o operador não escolheu, enviado como se fosse decisão dele. É exatamente a classe que a
   `v1.11.0a8b58.c3` fechou em `regimeTributario`, e que a `b64` fechou em `contribuinteIpi`.
2. **`DESCARTE` na edição** — a tela relê seis dos dez campos fiscais do response e reenvia; os
   outros quatro (`tipoItemSped`, `unidadeTributavelSigla`, `exTipi`, `codigoBeneficioFiscalPadrao`)
   não são relidos nem reenviados. Se o PATCH passasse, ele apagaria os quatro. É a mesma forma da
   `D54` que a `b64` achou no backend (`Crt` sem semântica de manutenção), do lado do cliente.

## 2. O que esta fatia faz, e o que ela não faz

**Faz**: o PATCH volta a passar nos dois caminhos, sem inventar classificação fiscal nenhuma.

**Não faz**: não põe campo fiscal novo na tela. `tipoItemSped`, `unidadeTributavelSigla`, `exTipi` e
`codigoBeneficioFiscalPadrao` como campos editáveis são a **`b65`**, que já tem inventário escrito
(`docs/fatias/v1.11.0a8b65-inventario.md`). Aqui `tipoItemSped` só **trafega**: é lido do response e
devolvido no request, para não ser apagado e para não derrubar a chamada.

## 3. Armadilhas

1. **Não escolher `tipoItemSped` por conta própria.** São 12 valores (`MercadoriaParaRevenda = 0` …
   `Outras = 99`) e a escolha é classificação fiscal do item, com efeito em SPED. Defaultar qualquer
   um seria trocar um `DEFAULT_SILENCIOSO` por outro, pior. Se o produto não tem `tipoItemSped`
   gravado, o bloco tem de ir **inteiramente em branco** — que é o caminho que o backend declara
   como válido e não-erro.

2. **`EstaEmBranco` é tudo-ou-nada.** Não existe meio-termo: ou os dez campos vão nulos, ou
   `tipoItemSped` é obrigatório. Então "mandar só o que o operador preencheu" **não** é solução —
   mandar `ncmCodigo` sem `tipoItemSped` continua dando 400.

3. **`TipoItemSped` começa em zero.** `MercadoriaParaRevenda = 0`. Tratar `0` como ausente
   (`if (!valor)`, `valor || null`) apaga a classificação mais comum do cadastro. Use checagem
   explícita de `null`/`undefined`.

4. **O `99` não é sequencial.** `Outras = 99` — não indexe por posição de array.

5. **O enum trafega como número.** Mesmo comportamento dos outros enums deste backend; a coluna de
   texto no banco é conversão do EF, persistência, não serialização.

6. **A prova durável do gate vai mudar.** `tests/unit/gateContractRequestFields.test.ts` tem
   `LACUNA_ESPERADOS_HOJE` com 8 itens e um `it` afirmando `toContain('8')`. Acrescentar
   `tipoItemSped` ao schema remove **um** item e deixa **7**. Carimbar isso faz parte da fatia —
   foi exatamente o que a `b62` e a `b63` não fizeram, e `test:unit` ficou vermelho por três
   versões.
