## 1. Objetivo

Quem tem `PRODUTOS_DADOS_FISCAIS_GERENCIAR` passa a conseguir classificar um produto para o SPED
(`tipoItemSped`), resolver a unidade tributável oficial da NF-e por busca (em vez de não ter onde
digitá-la), registrar EX-TIPI e código de benefício fiscal, e descrever o item no catálogo do
fornecedor ao vincular — os quatro campos que `AtualizarDadosFiscaisProdutoRequest`/
`VincularProdutoFornecedorRequest` já aceitam e a tela ainda não oferece.

## 4. Armadilhas conhecidas desta fatia

- **`AtualizarDadosFiscaisProdutoRequest` não faz merge — é substituição atômica dos dez campos.**
  `ProdutosPage.tsx` já reenvia o bloco inteiro sempre; os quatro campos novos entram no mesmo
  payload, nunca como chamada separada. Desenhar assumindo "salvar só o que mudou" está errado por
  contrato (inventário §3, confirmado pela `arquiteto-plataforma-frontend`).
- **`value` de `unidadeTributavelSigla` é a sigla, nunca um Id.** O backend resolve o Id no
  servidor; se o campo for montado copiando o padrão de `EntitySelect` (Guid-based) em vez do de
  `useUfCatalogo` (sigla-based), o Zod aceita a string errada sem erro de compilação e o defeito só
  aparece no 400 do backend (D60).
- **`tipoItemSped = 0` (`MercadoriaParaRevenda`) é valor válido, não "vazio".** Usar `value ?? null`
  no `Dropdown`, nunca `value || null` — o padrão já existe ao lado, em `tipoItemFiscal`
  (`ProdutoFormDialog.tsx:268-270`), copiar a mesma forma.
- **`unidadeTributavelSigla` sem opção sintética (`comSelecionado`) mostra vazio um valor gravado**
  quando a busca atual não traz aquela sigla na página — já corrigido duas vezes no repositório
  (ver `classeDeDefeito` acima). Não é escolha, é replicar a técnica.
- **`LACUNA_DESTINO` em `scripts/gate-contract-request-fields.mjs:363` já tem uma entrada órfã**
  (`tipoItemSped: 'b65'`, resolvida desde a `c2`) que nenhum teste acusa hoje — atualizar o mapa
  junto com o schema não é suficiente sozinho; esta fatia adiciona a asserção que impede a próxima
  entrada órfã de passar batido (`gate_estrutural`).
- **Vínculo de fornecedor não tem caminho de correção.** Não existe use case de atualização de
  `ProdutoFornecedor` no backend — só criação, recusada se já existe vínculo. Se o operador digitar
  `descricaoFornecedor` errado, não há UI de correção nesta fatia nem depois dela sem endpoint novo
  (pergunta B-11, `docs/PLANO-FRONTEND-ONDA-OPERACAO.md`). Não inventar botão de "editar vínculo".
